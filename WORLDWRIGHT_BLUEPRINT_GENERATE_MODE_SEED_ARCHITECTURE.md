# WorldWright Blueprint: Generate Mode Seed Architecture

Status: draft / generator subsystem blueprint  
Owner: Iron Man  
Purpose: define deterministic seeded world birth, named random streams, stage/domain/tile seeds, reproducibility guarantees, diagnostics, migration behavior, and forbidden shared-random shortcuts for Generate Mode.

Governing documents:

```text
WORLDWRIGHT_BLUEPRINT_GENERATE_MODE_GENERATOR_CONSTITUTION.md
WORLDWRIGHT_BLUEPRINT_GENERATE_MODE_SCOPE_AND_DOMAIN_MAP.md
```

---

## 1. Core Law

```text
Seed Architecture is the reproducibility spine of Generate Mode.

A WorldWright seed must not merely produce a random-looking world.
A WorldWright seed must produce a stable, inspectable, replayable birth record for a world and all of its generated domains.
```

Generate Mode must never rely on uncontrolled randomness.

The same world seed, generation profile, generator version, seed architecture version, and deterministic stage inputs must produce the same canonical generated source.

The seed system must support:

```text
macro world generation,
dormant micro tile readiness,
future micro tile activation,
stage diagnostics,
regression tests,
export reproducibility,
save/load round trips,
and future modular tool handoffs.
```

Most important rule:

```text
Adding, removing, or reordering work in one generator domain must not accidentally change unrelated domains.
```

---

## 2. Why Seed Architecture Comes First

Seed Architecture is the next generator subsystem because every later generated domain depends on it.

If seeds are weak:

```text
changing climate can accidentally change continents,
opening a micro tile can accidentally change macro terrain,
adding diagnostics can accidentally change the generated world,
export can fail to reproduce a heightmap,
regression tests can become unstable,
and save/load cannot prove that regenerated fields still belong to the same world.
```

A seed is not just a number.

In WorldWright, a seed is part of the world identity and source contract.

Seed Architecture must define:

```text
what seed produced the world,
which named streams produced each domain,
which stage version interpreted those streams,
which tile seeds support dormant local detail,
which diagnostics used independent randomness,
and which outputs are expected to remain stable across non-breaking changes.
```

## 3. Seed Ontology

WorldWright seed terms must be explicit.

### 3.1 World Seed

The World Seed is the root deterministic identity of the generated world.

It may be user-entered, generated by the app, imported, or derived from a project template.

It must be saved.

It must be displayed or inspectable.

It must not be replaced silently.

### 3.2 Seed Architecture Version

The Seed Architecture Version defines how the world seed is split into named streams and derived seeds.

Example:

```text
seedArchitectureVersion: generate-seed-architecture-v1
```

Changing this version may intentionally alter generated worlds.

If it changes, save/load and diagnostics must report it.

### 3.3 Generator Version

The Generator Version defines the generation code/logic that interprets seeds.

Seed stability requires both:

```text
same seed architecture,
same generator version or compatible migration behavior.
```

### 3.4 Named Stream

A Named Stream is a deterministic random source assigned to a specific domain or stage.

Examples:

```text
planet.foundation
geology.plates
geology.continents
terrain.birth
hydrology.basins
climate.baseline
biome.potential
resources.potential
settlement.suitability
microTile.registry
microTile.activation
export.sampling
diagnostics.sampling
```

Named streams prevent unrelated systems from stealing randomness from each other.

### 3.5 Domain Seed

A Domain Seed is derived from the world seed plus a stable domain name.

Examples:

```text
seed(worldSeed, 'domain:terrain.birth')
seed(worldSeed, 'domain:hydrology.baseline')
seed(worldSeed, 'domain:microTile.registry')
```

### 3.6 Stage Seed

A Stage Seed is derived for a specific generation stage within a domain.

Examples:

```text
seed(worldSeed, 'stage:terrain.birth:ridgeNoise')
seed(worldSeed, 'stage:hydrology.baseline:basinTieBreakers')
seed(worldSeed, 'stage:climate.baseline:humidityVariance')
```

### 3.7 Tile Seed

A Tile Seed is derived from world seed + tile ID + tile purpose.

Examples:

```text
seed(worldSeed, 'tile:F2-L8-X103-Y044:activation')
seed(worldSeed, 'tile:F2-L8-X103-Y044:preview')
seed(worldSeed, 'tile:F2-L8-X103-Y044:export')
```

Tile seeds must be stable even if the user opens neighboring tiles first.

### 3.8 Diagnostic Seed

A Diagnostic Seed is used for randomized sampling, test scenarios, or artifact selection.

Diagnostic seeds must not consume generator streams.

Diagnostics must never change canonical generation.

### 3.9 Export Reproducibility Seed

Export may require sampling or resampling.

If randomness is involved, export must use export-specific seeds.

Export seeds must not mutate source world generation.

### 3.10 Seed Manifest

The Seed Manifest records all important seed architecture data for a generated world.

It must be saved with the world.

## 4. Determinism Contract

The deterministic contract is:

```text
same world seed
+ same generation parameters
+ same seed architecture version
+ same generator version
+ same domain inputs
= same canonical generated source fields
```

This does not require every cache, debug visualization, or external artifact to be byte-identical forever.

It does require canonical generated source fields to be stable within a declared compatibility range.

### 4.1 Stable Outputs

The following should be stable within a compatible generator version:

```text
planet foundation,
macro geologic source fields,
base generated terrain source,
sea level source,
micro tile registry,
stable tile IDs,
tile seeds,
canonical generated IDs,
source field ownership,
initial sim proxy source.
```

### 4.2 Recomputable Outputs

The following may be regenerated from source:

```text
derived fields,
debug overlays,
preview meshes,
field summaries,
visual snapshots,
micro tile resolved caches,
export-prep rasters,
diagnostic reports.
```

### 4.3 Non-Stable Outputs

Some outputs may change if rendering, display, or export libraries change.

Examples:

```text
antialiasing of screenshots,
preview texture compression,
file timestamps,
external engine import artifacts,
performance timings.
```

These must not be treated as canonical world truth.

## 5. Forbidden Shared-Random Coupling

Shared-random coupling happens when multiple domains pull from the same random stream in sequence.

Forbidden example:

```ts
const rng = makeRng(worldSeed);
createContinents(rng);
createClimate(rng);
createRivers(rng);
createMicroTiles(rng);
```

This is forbidden because adding one random call in `createContinents` can change climate, rivers, and micro tiles.

Required pattern:

```ts
const seeds = createSeedManifest(worldSeed, generationProfile);
createContinents(seeds.stream('geology.continents'));
createClimate(seeds.stream('climate.baseline'));
createRivers(seeds.stream('hydrology.baseline'));
createMicroTiles(seeds.stream('microTile.registry'));
```

Even better, for tile/local work:

```ts
const tileSeed = seeds.tileSeed(tileId, 'activation');
activateMicroTile(tileId, tileSeed, macroContext);
```

Core law:

```text
No generator domain may depend on how many random numbers another unrelated domain consumed.
```

## 6. Seed Derivation Contract

Seed derivation must be deterministic, stable, and named.

The exact hash/RNG implementation may be chosen during implementation, but the blueprint requirements are fixed.

A derived seed should be based on:

```text
world seed,
seed architecture version,
generation profile identity,
stable stream name,
optional stage name,
optional object ID,
optional tile ID,
optional local coordinate key.
```

Example conceptual derivation:

```ts
function deriveSeed(parts: SeedDerivationParts): Seed64 {
  return stableHash64([
    parts.seedArchitectureVersion,
    parts.worldSeed,
    parts.generationProfileId,
    parts.streamName,
    parts.stageName ?? '',
    parts.objectId ?? '',
    parts.tileId ?? '',
    parts.coordinateKey ?? '',
  ].join('|'));
}
```

Rules:

```text
Stream names must be stable strings.
Stream names must not be localized user-facing labels.
Tile IDs must be stable.
Object IDs used in derivation must be source IDs, not transient UI IDs.
Derived seeds must be inspectable in diagnostics.
Changing stream names is a seed migration event.
```

## 7. RNG Contract

WorldWright must use a deterministic RNG implementation under its own control.

Forbidden:

```text
Math.random for canonical generation,
time-based randomness for canonical generation,
iteration-order-dependent object traversal,
unordered map traversal as generation authority,
randomness hidden inside rendering/export libraries,
diagnostics consuming canonical generator streams.
```

Required:

```text
explicit RNG creation from derived seeds,
repeatable outputs across supported platforms,
known numeric ranges,
no hidden global random state,
no shared mutable RNG between unrelated domains,
diagnostics able to report stream name and seed.
```

### 7.1 RNG Output Helpers

Seeded generation should use named helper functions rather than ad hoc randomness.

Examples:

```ts
rng.float01();
rng.floatRange(min, max);
rng.intRange(minInclusive, maxExclusive);
rng.bool(probability);
rng.pickWeighted(options);
rng.noise2D(x, y, streamSalt);
rng.noise3D(x, y, z, streamSalt);
rng.shuffleStable(items, itemKey);
```

### 7.2 Stable Weighted Choice

Weighted choice must be deterministic and inspectable.

The chosen option should be traceable to:

```text
stream name,
seed,
weights,
selection roll,
selected key.
```

### 7.3 Stable Shuffle

Shuffling must be stable by item identity, not by transient array order when source order is undefined.

## 8. Seed Manifest Data Contract

Every generated world should include a Seed Manifest.

```ts
interface GenerateSeedManifest {
  seedArchitectureVersion: string;
  generatorVersion: string;
  worldSeed: string;
  generationProfileId: string;

  rootSeedHash: string;

  streamRegistry: SeedStreamRegistryEntry[];
  domainSeeds: Record<string, string>;
  stageSeeds: Record<string, string>;

  tileSeedPolicy: TileSeedPolicy;
  diagnosticSeedPolicy: DiagnosticSeedPolicy;
  exportSeedPolicy: ExportSeedPolicy;

  migration?: SeedMigrationRecord[];
}
```

### 8.1 Seed Stream Registry Entry

```ts
interface SeedStreamRegistryEntry {
  streamName: string;
  ownerDomain: GenerateDomainName;
  purpose: string;
  stability: 'CANONICAL_STABLE' | 'DERIVED_STABLE' | 'DIAGNOSTIC_ONLY' | 'EXPORT_ONLY' | 'EXPERIMENTAL';
  mayAffectCanonicalSource: boolean;
  createdByStage?: string;
  consumedByStages: string[];
  notes?: string;
}
```

### 8.2 Tile Seed Policy

```ts
interface TileSeedPolicy {
  tileIdScheme: string;
  tileSeedDerivation: 'WORLD_SEED_PLUS_TILE_ID_PLUS_PURPOSE';
  tileSeedPurposes: string[];
  stableAcrossNeighborActivationOrder: boolean;
  stableAcrossViewportOrder: boolean;
}
```

### 8.3 Diagnostic Seed Policy

```ts
interface DiagnosticSeedPolicy {
  diagnosticStreamsSeparateFromCanonical: boolean;
  defaultDiagnosticStream: string;
  artifactSelectionStream?: string;
  scenarioSamplingStream?: string;
}
```

### 8.4 Export Seed Policy

```ts
interface ExportSeedPolicy {
  exportStreamsSeparateFromCanonical: boolean;
  exportSeedDerivation: 'WORLD_SEED_PLUS_EXPORT_PROFILE_PLUS_SOURCE_ID';
  outputMustRecordSeed: boolean;
}
```

## 10. Stage Seed Contract

Each generator stage must declare its seed use.

Example stage contract:

```ts
interface GenerateStageSeedContract {
  stageName: string;
  domainName: GenerateDomainName;
  canonicalStreams: string[];
  derivedStreams: string[];
  debugStreams: string[];
  diagnosticStreams: string[];
  exportStreams: string[];
  forbiddenStreams: string[];
  consumesRandomness: boolean;
  stableAcrossRefactor: boolean;
}
```

A stage fails seed readiness if:

```text
it calls RNG without a stream,
it consumes a stream owned by another unrelated domain,
it changes output when diagnostics are enabled,
it changes output when render order changes,
it uses iteration order from unstable objects,
or it cannot report which seeds affected output.
```

## 11. Micro Tile Seed Architecture

Micro tile seeds are critical because dormant tiles must activate later without depending on user navigation order.

Core law:

```text
A micro tile must activate from its tile ID, world seed, generation profile, and macro context.
It must not depend on which tiles were opened before it.
```

### 11.1 Tile Seed Purposes

Required tile seed purposes:

```text
preview,
activation,
localTerrainDetail,
localHydrologyDetail,
localSurfaceDetail,
localResourceDetail,
localSettlementContext,
exportHeightmap,
diagnosticSampling.
```

Example:

```ts
function deriveTileSeed(
  manifest: GenerateSeedManifest,
  tileId: string,
  purpose: TileSeedPurpose,
): Seed64 {
  return deriveSeed({
    seedArchitectureVersion: manifest.seedArchitectureVersion,
    worldSeed: manifest.worldSeed,
    generationProfileId: manifest.generationProfileId,
    streamName: `microTile.${purpose}`,
    tileId,
  });
}
```

### 11.2 Tile Seed Stability Rules

```text
Opening tile A must not change tile B.
Opening neighboring tiles first must not change the selected tile.
Viewport order must not affect tile generation.
Exporting a tile must not change its source.
Running diagnostics on a tile must not change its source.
Tile activation may read macro context, but it must not mutate macro context.
```

### 11.3 Tile Neighbor Randomness

If neighboring context needs randomness, it must be derived from stable neighbor IDs or edge IDs.

Example:

```text
edgeSeed = seed(worldSeed, 'tileEdge:F2-L8-X103-Y044:EAST')
```

Edge seed rules:

```text
Shared edges must derive the same seed from both neighboring tiles.
Edge IDs must be canonicalized.
Edge seeds must support seam continuity.
Edge seeds must be saved or reproducible.
```

## 12. Coordinate-Based Randomness

Some generation needs local random variation tied to coordinates rather than sequential RNG calls.

Use coordinate-keyed randomness for:

```text
terrain detail noise,
surface variation,
local biome mottling,
resource flecks,
diagnostic sampling grids,
export resampling tie-breakers.
```

Coordinate-based randomness should be based on:

```text
stream name,
world seed,
domain/stage,
coordinate key,
tile ID if local,
LOD/resolution if relevant.
```

Rule:

```text
Coordinate-based randomness must not change when traversal order changes.
```

Forbidden:

```ts
for (const cell of cellsInCurrentTraversalOrder) {
  cell.detail = rng.float01();
}
```

Preferred conceptual pattern:

```ts
for (const cell of cells) {
  cell.detail = randomAtCoordinate(stream, cell.stableCoordinateKey);
}
```

## 13. Seeded Noise Contract

Noise fields are allowed, but must be owned and named.

Noise may support:

```text
roughness,
local terrain variation,
coast irregularity,
bathymetry texture,
biome transition variation,
surface material variation.
```

Noise must not become the world spine.

Rules:

```text
Noise fields must have stream names.
Noise fields must have domain ownership.
Noise must be constrained by causal fields.
Noise must not overwrite geologic/process authority.
Noise parameters must be saved or reconstructable.
Noise must be diagnosable.
```

Forbidden:

```text
raw noise terrain as the primary world cause,
noise-only continents,
noise-only rivers,
noise-only biomes,
noise hiding failed authority.
```

## 14. Seed Stability and Versioning

Seeded output may evolve across major generator changes, but this must be explicit.

### 14.1 Stable Compatibility

Within a compatible seed architecture/generator version, canonical source should remain stable.

### 14.2 Breaking Generator Change

A breaking generator change may alter canonical output.

If this happens:

```text
generator version must change,
seed architecture version may change,
migration behavior must be documented,
old saves must report compatibility status,
regression baselines must be updated deliberately.
```

### 14.3 Migration Strategy

Seed migration must not be silent.

Possible migration outcomes:

```text
EXACT_REPLAY_SUPPORTED,
SOURCE_COMPATIBLE_RECOMPUTE,
PARTIAL_RECOMPUTE_WITH_REPORT,
LEGACY_WORLD_LOCKED,
MANUAL_REGENERATION_REQUIRED.
```

Example:

```ts
interface SeedMigrationRecord {
  fromSeedArchitectureVersion: string;
  toSeedArchitectureVersion: string;
  fromGeneratorVersion: string;
  toGeneratorVersion: string;
  migrationMode:
    | 'EXACT_REPLAY_SUPPORTED'
    | 'SOURCE_COMPATIBLE_RECOMPUTE'
    | 'PARTIAL_RECOMPUTE_WITH_REPORT'
    | 'LEGACY_WORLD_LOCKED'
    | 'MANUAL_REGENERATION_REQUIRED';
  notes: string;
}
```

## 15. Save/Load Contract

Save/Load must persist enough seed data to prove where generated fields came from.

Required saved seed fields:

```text
world seed,
seed architecture version,
generator version,
generation profile ID,
root seed hash,
stream registry or registry version,
tile seed policy,
diagnostic seed policy,
export seed policy,
seed migration records if any.
```

Save/Load must not preserve only final visuals.

Load must be able to answer:

```text
Can this world be replayed exactly?
Can derived fields be recomputed safely?
Have seed rules changed?
Are micro tile seeds still valid?
Are export artifacts stale?
Is this a legacy world that needs migration/reporting?
```

## 18. Tests

Required tests:

```text
same seed produces same canonical generated source,
different seeds produce meaningfully different worlds,
adding diagnostics does not change generated source,
opening micro tiles in different orders produces same tile output,
export does not mutate source world,
save/load preserves seed manifest,
derived recompute from saved seeds is stable,
named streams do not shift when unrelated stages consume more random values,
Math.random is not used in canonical generation,
stage seed contracts report consumed streams,
tile edge seeds are symmetric for neighbor edges,
legacy seed architecture migration reports status.
```

Regression tests must include known seeds.

Some seeds should become canonical audit seeds for generator CI.

## 20. User Contract

The user should be able to trust that a seed means something.

User-facing rules:

```text
The same seed should recreate the same world when using the same compatible generator profile.
The app should warn when generator changes may alter old seeds.
The user should be able to inspect/copy/share the world seed.
The user should not lose authored work because a seed recompute silently changed base truth.
Micro tile activation should not depend on browsing order.
Exported files should identify their source world/tile/seed.
```

The user does not need to understand the full seed architecture, but the system must be able to explain it when needed.

---

## 21. Failure Modes

Seed Architecture fails if:

```text
same seed produces different canonical worlds without version/migration explanation,
Math.random affects canonical generation,
diagnostics change generated output,
render order changes generated output,
opening tiles in a different order changes tile results,
adding a random call in one domain changes another unrelated domain,
export lacks source seed metadata,
save/load loses seed manifest,
old worlds silently change after generator update,
stream ownership is unknown,
source/caches/debug/export randomness are mixed,
shared RNG state crosses domain boundaries,
unstable object iteration affects generated fields.
```

Catastrophic failure:

```text
WorldWright cannot prove that a generated world belongs to its seed.
```

## 22. Forbidden Shortcuts

```text
Do not use Math.random for canonical generation.
Do not use time-based randomness for canonical generation.
Do not use one shared RNG for the whole generator.
Do not let diagnostics consume canonical generator streams.
Do not let export consume canonical generator streams.
Do not derive tile detail from activation order.
Do not rely on unordered object/map traversal for generation authority.
Do not hide seed changes under generic generator updates.
Do not change stream names without migration/reporting.
Do not store final visuals instead of seed/source data.
Do not treat seeded noise as the world spine.
Do not allow a generator stage without a seed contract if it uses randomness.
```

Seed Architecture is blueprint-ready when it defines:

```text
world seed,

domain seeds,
stage seeds,
tile seed policy,
diagnostic seed policy,
export seed policy,
RNG contract,
coordinate-based randomness contract,
noise contract,
version/migration behavior,
save/load behavior,
export reproducibility behavior,
diagnostics,
tests,
failure modes,
forbidden shortcuts.
```

Implementation is ready only when:

```text
canonical generation has no uncontrolled randomness,
each random-consuming stage declares streams,
seed manifests are saved,
save/load preserves seed identity,
diagnostics prove stream separation,
micro tile activation is order-independent,
and regression seeds stay stable within compatibility rules.
```

```text
Seed Architecture is not decoration.
It is the reproducibility spine of Generate Mode.

The seed system must let WorldWright birth a world, prove where it came from, deepen it later through micro tiles, export it, save it, load it, diagnose it, and protect it against accidental unrelated changes.

No generator domain may depend on how many random numbers another unrelated domain consumed.
```
